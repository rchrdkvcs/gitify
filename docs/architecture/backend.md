# Backend

## Routes et rendu

`PagesController` charge les données métier et rend les pages Inertia. `/`, `/explore`, `/issues` et `/projects/:owner/:name` sont publiques ; le jeton GitHub utilisé est décrit dans « Composition et jetons GitHub ». `/favorites`, `/profil`, `/preferences` et `/onboarding` exigent une session ; les visiteurs sont redirigés vers `/`.

Seules les routes `/api/projects/:id/favorite` (ajout et retrait d'un favori) et `/api/onboarding` (réponse enregistrée en arrière-plan) répondent en JSON ; le fil et les favoris sont des pages Inertia (`/explore`, `/favorites`). Elles utilisent la même session et la même protection CSRF que les pages. Il n'y a plus de configuration CORS ni de documentation OpenAPI pour une API séparée.

## Authentification

`/auth/github/redirect` lance OAuth via Ally ; `/auth/github/callback` vérifie la réponse, crée ou actualise l'utilisateur avec `AuthService`, puis ouvre la session. L'identifiant GitHub, numérique au runtime Ally, est normalisé en chaîne stable : un changement d'email vérifié conserve les préférences et les favoris. La première connexion exige un email vérifié, sans réserver une adresse non vérifiée. Un compte historique (sans identifiant GitHub) est lié dès qu'une connexion présente le même email vérifié par GitHub ; il conserve ses préférences et ses favoris. Si cet email appartient déjà à une autre identité GitHub, la connexion est refusée (409). Un utilisateur reconnu par son identifiant ne prend un nouvel email vérifié que s'il est libre ; sinon il garde l'email enregistré et se connecte normalement. Aucun appel HTTP n'a lieu dans la transaction ; un verrou consultatif par identité GitHub sérialise les premières connexions concurrentes. Le callback redirige vers `/onboarding` tant que le parcours guidé n'est ni terminé ni reporté, sinon vers `/explore` (`OnboardingService.landingPath`). `DELETE /auth/logout` ferme la session et redirige vers `/`.

`UserTransformer` expose le profil partagé avec Inertia et exclut le jeton GitHub. Les lectures de projets composent des projections publiques communes aux pages, avec des dates ISO et un état favori propre au lecteur. `ProjectTransformer` définit la projection de liste, qui exclut le README et les détails ; `ProjectDetailTransformer` ajoute les détails et les contributeurs. Le module de lecture retourne leurs objets publics sans exposer Lucid aux contrôleurs. Chaque transformer type le retour de `toObject()` avec le contrat de `shared/types`.

## Onboarding et préférences

`shared/preferences.ts` est la source unique des choix possibles : `languageCatalog`, `experienceLevelCatalog` (avec le niveau de recherche GitHub associé), `contributionTypeCatalog` et `topicSuggestions`. Il fournit aussi `difficultyForLevel` et `normalizePreferenceLanguages`. `shared/stored_preferences.ts` porte `normalizeUserPreferences` (lit l'ancien et le nouveau format), `shared/language_inference.ts` porte `inferPreferredLanguages` et `shared/preference_summary.ts` porte `summarizePreferences` (libellés affichés par le profil et l'écran de fin). Toute fonctionnalité qui a besoin du niveau, des langages ou des façons de contribuer d'un utilisateur lit `user.preferences` (déjà normalisé par le modèle) et ces helpers.

`OnboardingController` et `OnboardingService` gèrent le parcours :

`shared/onboarding.ts` est la source unique du parcours : liste des étapes et champ de préférence auquel chacune répond, bornes, reprise, transitions et enregistrement d'une réponse. Le validator en dérive ses bornes, la page en dérive son affichage.

- `GET /onboarding` rend la page avec la question de reprise et une prop différée `suggestedLanguages`, calculée depuis les dépôts de l'utilisateur (`GET /user/repos`) ; un échec GitHub ne donne simplement aucune suggestion.
- `PATCH /api/onboarding` (JSON) enregistre une réponse confirmée et l'étape atteinte. La réponse doit porter exactement le champ de son étape, sinon 422.
- `PUT /onboarding` valide toutes les réponses, les enregistre et renseigne `onboarded_at`.
- `POST /onboarding/skip` renseigne `onboarding_skipped_at` et redirige vers le catalogue.

`PUT /auth/preferences` valide les mêmes champs avec Vine et passe par le même `OnboardingService.completeWith` que `PUT /onboarding` : il enregistre les préférences, termine l'onboarding s'il ne l'était pas et redirige vers l'exploration. Les validators normalisent, dédupliquent et bornent les choix ; les identifiants inconnus sont refusés. Les critères des fils (`app/feed_criteria/`) dérivent les filtres par défaut des préférences.

## Composition et jetons GitHub

`providers/app_provider.ts` est la racine de composition : il lie `GitHubAdapter` (classe abstraite, contrat de l'adapter) à `GitHubApiClient`, `GitHubCredentials` au jeton serveur, puis les synchronisations, les services de fil et `OnboardingService`. Aucun service n'est exporté comme instance ; les contrôleurs reçoivent leurs dépendances par `@inject()` et le seeder les résout via `app.container`. Les fichiers qui injectent par constructeur importent leurs dépendances comme valeurs (métadonnées de décorateur), d'où l'exception `consistent-type-imports` dans `oxlint.config.ts`.

`GitHubCredentials` (`app/services/github/github_credentials.ts`) est le seul lecteur de `GITHUB_SERVER_TOKEN`. `readerFor(user)` construit le lecteur d'une requête : `{ userId, token, source }`, avec `source` à `user` (jeton de l'utilisateur connecté), `server` (visiteur ou utilisateur sans jeton) ou `none` (aucun jeton serveur : seules les données en cache sont servies, sans appel GitHub). `server()` sert la vitrine et le seeder. Les synchronisations reçoivent `CredentialFallbackAdapter`, qui décore l'adapter : si un appel avec un jeton utilisateur échoue par `GitHubAuthError` ou `GitHubRateLimitError`, il est rejoué une fois avec le jeton serveur. Les suggestions de l'onboarding n'utilisent que le jeton de l'utilisateur, sans repli.

En test, `tests/bootstrap.ts` lie par défaut `GitHubAdapter` à un adapter factice et retire le jeton serveur : l'adapter de production n'est jamais atteint. `swapGitHub` et `restoreGitHub` (`tests/helpers/github_container.ts`) remplacent l'adapter et le jeton serveur d'un test HTTP via `app.container.swap`.

## Score d'accueil des débutants

`shared/newcomer_score.ts` est un module pur : `computeNewcomerScore(input, now)` applique des poids explicites (`newcomerScoreWeights`) et des règles de normalisation (`newcomerScoreRules`), définis dans `shared/newcomer_score_rules.ts`, puis retourne le score, sa couverture et le détail de chaque signal (valeur, ratio, points). `newcomerScoreInputFromInsights` lit un instantané `insights`, y compris ceux antérieurs au score.

La requête GraphQL des détails récupère en plus les 25 dernières issues et PR avec leurs premiers commentaires et revues, la dernière PR fusionnée et l'assignation des « good first issue ». `assembleRepositorySnapshot` (`app/services/github/repository_snapshot.ts`) en déduit `insights.contributorActivity` via `summarizeContributorActivity` (`app/services/github/contributor_activity.ts`) : médiane de première réponse d'un mainteneur, PR externes fusionnées ou fermées. `storeRepositorySnapshot` (`app/services/github/repository_snapshot_store.ts`), appelé par `GitHubSyncService.fetchProjectDetails`, calcule le score dans la même transaction que l'instantané : la valeur va dans `newcomer_score`, le détail des signaux dans `newcomer_score_details`, et l'état archivé dans `is_archived`. `Project.newcomerScoreReport` recompose le score complet pour les transformers. Le catalogue trie par `newcomer_score DESC NULLS LAST`, filtre par score minimal et exclut les dépôts archivés par `is_archived`.

## Projets

Les services de projets vivent dans `app/services/feeds/`, un module par responsabilité : `ProjectShowcase` (vitrine), `ProjectCatalogue` (catalogue `/explore`), `popularTopics`, `ProjectDetailReader` (page projet) et `project_favorites.ts` (favoris). `visible_projects.ts` est le seul propriétaire des règles de visibilité : `listedProjects` sert la vitrine, le catalogue, les sujets et le seeder (appartenance à une recherche correspondante, dépôt non archivé) ; `reachableProject` sert la page projet, qui reste accessible pour tout dépôt stocké, y compris archivé ou importé uniquement par une issue. La sélection s'appuie sur les appartenances aux recherches, indépendantes de l'identité des dépôts. Le catalogue renseigne l'état des favoris. Chaque langage vérifie sa fraîcheur, même lorsque le stock global est important. `cachedFeedPage` (`cached_feed_page.ts`), commun au catalogue et au fil d'issues, reçoit les actualisations de recherche, la requête et la page : seule la première page actualise, puis il renvoie les éléments, la pagination et `refreshState`, qui indique si le résultat est prêt, en cours d'actualisation, dégradé ou indisponible. Les projets en cache restent disponibles en cas de panne GitHub.

La vitrine utilise la même politique de fraîcheur quand un jeton serveur existe. Elle tire ses dépôts au hasard via une source aléatoire injectable, conserve les données en cache lors d'un échec distant (journalisé par le logger Adonis) et limite l'enrichissement des détails à deux dépôts par requête. Chaque carte reçoit ses deux principaux contributeurs, avec un ordre déterministe.

La page projet ne bloque jamais sur GitHub. `ProjectDetailReader` sert d'abord les données en base : des détails expirés (`cache.detailsCacheHours`) sont actualisés en arrière-plan ; des détails jamais chargés sont livrés par la prop différée Inertia `details` (annoncée par `detailsPending`, la page affiche un squelette dans `<Deferred>`), tandis que `project` reste la projection de base. `GitHubSyncService.fetchProjectDetails` mutualise les actualisations simultanées d'un même projet dans le processus. Un échec renseigne `projects.details_retry_after` (`retryAfterFailure` : `cache.detailsRetrySeconds` ou heure de reprise du quota) ; `needsDetailsFetch` ne relance pas GitHub avant cette date, et un enrichissement réussi l'efface. Les contributeurs sont écrits en un seul `INSERT … ON CONFLICT (project_id, github_user_id) DO UPDATE`.

`GitHubApiClient` compose l'adapter GitHub : `GitHubTransport` (délai borné couvrant la requête et le corps de réponse, issues déclarées par endpoint comme `absent`, `empty` ou `pending`), les requêtes GraphQL (`github_queries.ts`) et un mapper par endpoint. Il renvoie un dépôt normalisé unique (`GitHubRepository`, licence `NOASSERTION` remplacée par son nom, page d'accueil vide à `null`) pour les deux recherches, et un instantané complet (`getRepositorySnapshot`) qui échoue entièrement si l'une de ses parties échoue. Les échecs sont typés (`github_errors.ts`) : `GitHubAuthError` (401, 403 sans quota), `GitHubRateLimitError` (429 ou 403 avec quota épuisé, avec heure de reprise), `GitHubUnavailableError` (5xx, délai, réseau), `GitHubNotFoundError`, `GitHubInvalidResponseError`. Les absences attendues de README ou de release sont distinguées des erreurs ; une réponse 204 des contributeurs représente une liste vide. `GitHubSyncService` et `OnboardingService` acceptent un adapter GitHub et une horloge ; les tests fournissent un adapter contrôlé (`tests/helpers/fake_github_adapter.ts`) et une base PostgreSQL dédiée. La politique de fraîcheur des instantanés de recherche (`app/services/search_freshness/`) est commune aux deux synchronisations : `SearchFreshnessPolicy.ensureFresh` reçoit une clé de critère opaque, un TTL, un magasin d'instantané (lecture et écriture de la ligne de cache du critère) et l'étape d'import, puis vérifie le TTL sous un verrou transactionnel PostgreSQL pour coordonner plusieurs processus. Un budget de recherches (`SearchPermits`, deux par processus, instance injectable) réserve une connexion pour un appel distant ; les autres servent le résultat en cache avec un état d'actualisation différée. Les échecs reportent la prochaine tentative de 60 secondes, ou jusqu'à l'heure de reprise d'une `GitHubRateLimitError`, avec une trace partagée en base. Les deux imports enregistrent les dépôts par `upsertRepositories` (`repository_identity.ts`), seul module qui pose le verrou d'identité d'un dépôt et écrit `projects.difficulty`. Toutes les recherches importent jusqu'à 100 dépôts, y compris celles lancées par la vitrine et le seeder ; les limites de présentation n'altèrent pas le stock du fil. Un import réussi remplace les appartenances du critère ; l'enrichissement remplace les contributeurs et les métadonnées atomiquement. Les limites et durées de cache restent dans `config/gitify.ts`.

## Fil d'issues

`IssueFeed` (`app/services/feeds/issue_feed.ts`) sert `/issues`. `parseIssueFilters` (`app/feed_criteria/issue_criteria.ts`) et `parseExploreFilters` (`explore_criteria.ts`) sont deux configurations de `defineFeedCriteria` (`feed_criteria.ts`) : un descripteur par filtre (paramètre, lecture, valeur issue des préférences). Un filtre présent dans la query string, même vide, remplace la préférence correspondante ; un filtre absent la reprend. Le catalogue `shared/issues.ts` définit les types d'issue (`good-first-issue`, `help-wanted`, `documentation`), le label GitHub recherché pour chacun, le type de contribution et le niveau qu'il sert (`defaultIssueKind`), et la lecture des signaux depuis les labels. Les langages viennent de `shared/preferences.ts`.

`GitHubIssueSyncService` reprend la politique de fraîcheur des recherches de dépôts pour chaque couple `(language, kind)` : TTL de 6 heures (`cache.issueFetchTtlHours`), verrou consultatif PostgreSQL, budget de recherches distantes partagé avec `GitHubSyncService` et report après un échec, via la même politique de fraîcheur. L'adapter appelle `searchIssues`, une recherche GraphQL qui renvoie l'issue et son dépôt. L'import écarte les dépôts archivés ou privés et les issues fermées par une pull request ouverte (`closedByPullRequestsReferences`), enregistre ou met à jour le dépôt sous le même verrou d'identité que les recherches de dépôts, puis remplace les appartenances du critère. Les issues qu'aucune recherche ne liste plus sont supprimées ; les verrous par issue empêchent un autre critère de les rattacher pendant ce nettoyage. Seule la première page déclenche ces actualisations ; `refreshState` a la même signification que pour le catalogue. `IssueTransformer` définit la carte transmise au navigateur.

La pagination des favoris normalise et ramène les pages à la dernière page disponible, avec un ordre stable par date puis identifiant. Après suppression, le navigateur relit la page canonique.
